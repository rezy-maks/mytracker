# План развития mytracker

План отражает текущее направление проекта. Архитектуру, API и формат хранения будем уточнять по мере появления требований, а не фиксировать заранее.

## Уже реализовано в прототипе

- Настольное приложение для Windows на Kotlin/JVM и Compose Multiplatform.
- Главный экран, каталог и категории «Фильмы», «Аниме», «Сериалы».
- Группировка каталога по статусам: «Хочу посмотреть», «Просмотрено», «Брошено».
- Добавление и удаление произведений; подтверждение удаления.
- Изменение статуса, оценки и рецензии с сохранением по кнопке «Готово» и отменой по кнопке «Назад».
- Личные заметки с системной датой; заметки можно добавлять и удалять.
- Просмотр сезонов и заметки к ним. Ручное добавление сезонов отключено.
- Локальное файловое хранилище с версионированием и тестами чтения, записи и миграций.

## Ближайшие улучшения

- Сделать генерацию ID произведений надёжной и уникальной.
- Вынести правила модели из UI и определить проверки для статуса, оценки, названия, заметок и сезонов.
- Добавить обработку ошибок чтения и записи: показывать причину, сохранять исходный файл при сбое и не заменять его пустыми данными автоматически.
- Добавить Compose UI-тесты для навигации, группировки, создания и редактирования записей, оценки просмотренного произведения, отмены изменений и подтверждения удаления.
- Продолжать проверять `jvmTest` при изменениях хранилища и модели.

## Выбор и подключение API агрегатора

- Выбрать источник данных и проверить доступность API, ограничения, условия использования и требования к атрибуции.
- Добавить поиск произведения по названию и выбор конкретного результата, чтобы ручной ввод постепенно заменить каталогом источника.
- Хранить внешний ID произведения и нужные метаданные, чтобы повторно находить запись у выбранного источника.
- Подгружать сезоны для сериалов и аниме из агрегатора; ручное создание сезонов не планируется.
- Продумать поведение при отсутствии сети, ошибках API и недоступности источника.

## Хранение данных и надёжность

- Выбрать формат хранения перед крупной интеграцией: версионированный файл, локальная БД (например, SQLite) или серверная БД (например, PostgreSQL).
- Сравнить варианты по работе офлайн, резервному копированию, синхронизации между устройствами, развёртыванию и сопровождению. PostgreSQL оправдан при наличии серверного сценария; для локального приложения отдельно оценить SQLite.
- После выбора хранилища определить границу репозитория, транзакции и необходимость выполнять операции вне UI-потока.
- Перед релизом решить, нужны ли миграции старых данных. Если каталог всё ещё содержит только тестовые данные и совместимость не нужна, можно удалить тестовое хранилище и оставить чистую схему одной версии. Если появятся реальные пользовательские данные, миграции и резервное копирование нужно сохранить.

## Архитектура и качество кода

- По мере роста разделить большой `App.kt` на экраны и компоненты с отдельной ответственностью.
- Вынести состояние каталога и бизнес-правила из Compose UI; определить интерфейс между экраном и источником данных.
- Перейти от отображаемых строк категорий к стабильным ID, особенно перед подключением API.
- Добавить автоматическую проверку форматирования и базовый CI для сборки и тестов.

## Подготовка Windows-релиза

- Подготовить иконку, версию приложения и инструкцию установки/обновления.
- Проверить чистую установку, запуск без существующего каталога, резервное копирование и восстановление данных.
